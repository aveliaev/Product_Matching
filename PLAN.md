# План: WDC Computers — дубль или нет

## 1. Постановка задачи

- **Вход:** пара офферов с разных сайтов. Используем `title`, `description`, `brand`, `price`, `specTableContent`, `keyValuePairs`.
- **Выход:** вероятность того, что оба оффера описывают один и тот же физический товар. Решение «дубль / не дубль» получаем через порог.
- **Тип задачи:** бинарная классификация пар (entity matching). Положительных пар примерно 14–27% в зависимости от выборки.
- **Главная сложность — «трудные негативы».** Например, RX 480 и RX 550 одного бренда: текст почти одинаковый, но модель другая. Отличие часто сидит в одном токене, в номере модели или в цифре.

### Данные

| Файл | Пар | 1 / 0 |
|---|---|---|
| `computers_gs.json` (test, ручная разметка) | 1 100 | 300 / 800 |
| `computers_train_small.json.gz` | 2 834 | 722 / 2 112 |
| `computers_train_medium.json.gz` | 8 094 | 1 762 / 6 332 |
| `computers_train_large.json.gz` | 33 359 | 6 146 / 27 213 |
| `computers_train_xlarge.json.gz` | 68 461 | 9 690 / 58 771 |

Формат — JSON Lines (`pd.read_json(path, lines=True)`).

Заполненность полей:

| Поле | Train (xlarge) | Test |
|---|---|---|
| title | 100% | 100% |
| description | 69% | 93% |
| brand | 50% | 60% |
| specTableContent | 31% | 37% |
| price | 17% | 23% |

- **`title` — основной сигнал**, остальные поля дополнительные. Медианная длина заголовка 14 слов.
- **Train и test распределены по-разному.** В test описания заполнены заметно чаще. Модель, которая сильно опирается на описание, может вести себя на test не так, как на валидации.
- **Режим «знакомые товары».** Все кластеры (товары) из test встречаются в train, 71% самих офферов из test тоже есть в train, при этом сами пары не повторяются. Значит, мы проверяем «узнать знакомый товар в новой паре», а не обобщение на новые товары.
- **Утечка:** `cluster_id` и `identifiers` не используем как признаки, потому что разметка построена по ним.

## 2. Разбиение данных

- **Test** = `computers_gs.json` (1 100 пар). Подбор параметров и порогов на нём не делаем. Смотрим только в конце этапа, чтобы зафиксировать результат.
- **Validation** — 20% от train, стратифицированно по `label`, с фиксированным seed. ID пар сохраняем в файл, чтобы все модели, классические и DL, работали на одном и том же разбиении.
- **Размер train:** основные эксперименты ведём на `medium` или `large`, итоговые модели прогоняем на всех четырёх размерах и строим кривую обучения.
- **По итогам EDA** (`EDA.md`): test заметно сложнее train, там намного больше трудных негативов. Поэтому на val дополнительно считаем F1 на **трудном подмножестве** (негативы с высоким cosine заголовков и позитивы с низким). ~~Модели сравниваем в первую очередь по нему.~~ Эксперименты этапа 2 показали, что эта метрика шумная и хуже предсказывает test (ρ = 0.61), чем обычный val F1 (ρ = 0.97). Основной критерий выбора — val F1, трудный F1 только логируем. Выборки разных размеров не вложены друг в друга, поэтому val вырезаем отдельно из каждой.

## 3. Метрики

- **Основная — F1 по положительному классу.** Это стандарт для WDC, значит, результаты можно сравнивать со статьями.
- **Дополнительные:**
  - Precision и Recall — понимать, какого типа ошибки делает модель;
  - PR-AUC — качество ранжирования, не зависящее от порога;
  - ROC-AUC можно логировать, но при таком дисбалансе он малоинформативен.
- **Порог** подбираем на validation по максимуму F1, а к test применяем уже выбранный.

## 4. Как понять, что стало лучше

В test всего 300 положительных пар, поэтому F1 шумит примерно на ±2 пункта. Разница в 0.5 пункта может ничего не значить. Протокол:

1. **Доверительный интервал:** bootstrap по парам test (1 000 повторов) даёт 95% ДИ для F1.
2. **Парное сравнение моделей:** paired bootstrap на одних и тех же ресэмплах (распределение ΔF1) плюс тест Макнемара по несовпадающим предсказаниям. **«Улучшение» засчитываем, только если 95% ДИ для ΔF1 не включает 0.**
3. **Seeds для DL:** 3–5 запусков с разными seed, в отчёт идёт mean ± std. Одному удачному seed не верим.
4. **Сохраняем предсказания** каждой модели на val и test (score по каждому `pair_id`). Тогда любые две модели можно сравнить позже без переобучения.

## 5. Инфраструктура (общая для ML и DL)

- **Единый интерфейс модели:** `fit(train, val)` и `predict_proba(pairs) -> scores`. Классика и трансформеры подключаются одинаково.
- **Один модуль оценки:** метрики, выбор порога, bootstrap, сравнение двух моделей.
- **Общая сериализация пары в текст**, например `[COL] title [VAL] ... [COL] brand [VAL] ...` в стиле Ditto. Она пригодится и для TF-IDF, и для трансформеров.
- **Лог экспериментов:** CSV или MLflow. В каждой записи: модель, конфиг, размер train, seed, метрики на val и test, путь к предсказаниям.

## 6. Этапы

**Этап 0. EDA.** ✅ Готово, выводы в `EDA.md`.

**Этап 1. Тривиальные бейзлайны** — «пол», ниже которого падать нельзя:
- ✅ `baseline.py`, результаты в `results.csv`: cosine TF-IDF заголовков с порогом — F1 test ≈ 0.57; 9 признаков похожести + логрег — F1 test 0.74 (small) … 0.75 (xlarge);
- совпадение извлечённого номера модели (регулярками).

**Этап 2. Классический ML:** 🔄 первая серия готова — `experiments.py`, отчёт `REPORT_classic.md`. Лучшее: 9 признаков + RandomForest / бустинг, F1 test ≈ 0.85 (xlarge). Полная чистка с удалением хвостов магазинов вредит, по умолчанию лёгкая чистка.
- чистка текста: `@en`, `null`, хвосты с названием магазина (`| OcUK`, `cdw.com`);
- признаки похожести (cosine по словам и символам, Jaccard, совпадение бренда, пересечение и различие кодов моделей и чисел — по EDA это самый сильный сигнал) + логистическая регрессия. Цену почти не используем, она редко заполнена;
- те же признаки + градиентный бустинг (LightGBM);
- TF-IDF-векторы пары `|a−b|`, `a*b` + логистическая регрессия;
- разбор ошибок: на каких парах модель ошибается.

**Этап 3. DL (трансформеры):**
- кросс-энкодер: `[CLS] оффер A [SEP] оффер B` → классификация. Начинаем с BERT-base или RoBERTa-base, только на title;
- добавляем description и спеки, сериализация в стиле Ditto;
- аугментации: обмен сторон A↔B, выкидывание токенов;
- модели крупнее или предобученные на e-commerce;
- опционально: bi-encoder (быстрее, пригоден для поиска кандидатов) и LLM zero-/few-shot для сравнения.

**Этап 4. Итог.** Сводная таблица всех моделей на test с ДИ, кривые обучения по размерам train, выводы.

Ориентир по литературе: на WDC Computers трансформеры обычно заметно обходят классику, особенно на маленьких train. Точные цифры сверим со статьями (Peeters & Bizer, Ditto), когда дойдём до этапа 3.

**Практическое замечание про DL:** BERT-base на Mac (MPS) нормально учится на small и medium. На xlarge (68 тыс. пар × несколько seed) будет долго, возможно, понадобится Colab или другая GPU.
